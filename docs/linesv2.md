## Как мы работаем с линиями — полный путь

### 1. Запрос с клиента

После жеста (debounce ~280 мс) фронт шлёт:

`GET /api/maps/{map_id}/features?bbox=west,south,east,north&zoom=N&layers=…`

- `bbox` — текущий viewport (WGS84).
- `zoom` — округлённый zoom карты. **В GIS не уходит**; нужен только нашему backend для политики упрощения/лимитов.
- Слои — если выбраны не все.

Линии **не** запрашиваются отдельным API: приходят вместе с точками одним FeatureCollection.

---

### 2. Upstream GIS

Backend (`GisReader`) вызывает GIS:

`GET …/maps/{id}/features?bbox=…&layers=…`

GIS отдаёт до **40 000** объектов, среди них Point / LineString / Polygon, стиль часто «размазан» по `properties`. Может быть `truncated: true`. Пагинации нет.

Узкое место первого показа на малом зуме — в основном **этот** ответ, не отрисовка.

---

### 3. Нормализация на backend

В `process_feature_collection`:

1. Полигоны и прочее **отбрасываются**.
2. Остаются только `Point` и `LineString`.
3. Стиль линии собирается во вложенный `properties.style`: `lineColor`, `lineWidth`, `lineOpacity`, …

Классификации «важная/неважная линия» нет — дальше только геометрия, zoom и случайность.

---

### 4. Конвейер именно для линий

Порядок сейчас такой (это важно для скорости):

#### A. Пресэмпл целых линий (до упрощения)

`GIS_MAX_LINE_VERTICES` (по умолчанию 5000) →  
`cap = max(64, max_vertices // 4)` → при 5000 это **1250** линий.

Если линий из GIS больше — `random.sample`, остальные выкидываются **целиком**.  
Иначе на малом зуме мы бы гоняли Douglas–Peucker по десяткам тысяч трасс.

Флаг `lines_thinned` / общий `thinned` в ответе.

#### B. Допуск упрощения по zoom

Из `GIS_LINE_SIMPLIFY_METERS`, например:

`0:50,12:20,14:8,16:2,18:0`

Берётся пара с наибольшим порогом `≤ текущего zoom`. Значение — **метры**. `0` = без геометрического упрощения (только лимиты, если включены).

| Zoom | Типичный допуск |
|---|---|
| ≤11 | 50 м |
| 12–13 | 20 м |
| 14–15 | 8 м |
| 16–17 | 2 м |
| ≥18 | 0 (без DP) |

#### C. Cap вершин на одну линию + stride

По допуску выставляется жёсткий потолок вершин **на линию**:

| Допуск | Cap на линию |
|---|---|
| ≥40 м | 8 |
| ≥20 м | 12 |
| ≥8 м | 24 |
| ≥2 м | 48 |
| меньше | 128 |

Если вершин больше — **stride downsample**: равномерно оставляем first/last и точки между ними. Это O(n), дёшево.

#### D. Douglas–Peucker (не всегда)

- На грубом допуске (`≥ 20` м), если после stride длина уже ≤ cap — **DP пропускаем** (stride уже сделал грубую работу).
- Иначе — свой Douglas–Peucker: допуск в метрах, расстояние через локальное приближение `cos(lat)`.

`simplify.js` на клиенте **не** используем.

#### E. Бюджет вершин на весь ответ

Считается сумма вершин всех оставшихся линий.  
Если `> GIS_MAX_LINE_VERTICES` — линии в случайном порядке кладутся в «корзину», пока бюджет не заполнится; что не влезло — снова **целыми** наружу.

`0` в `GIS_MAX_LINE_VERTICES` отключает и пресэмпл-кап, и финальный бюджет (для мобилы плохо).

---

### 5. Ответ клиенту

Один FeatureCollection:

- `features` = точки + линии (уже упрощённые);
- `truncated` — обрезал GIS;
- `thinned` — проредили мы (точки и/или линии);
- `meta.line_count`, `simplify_tolerance_m`, …

В UI при `truncated || thinned` — «данные неполные».

Координаты линий в ответе — GeoJSON `[lon, lat]`.

---

### 6. Отрисовка на карте

Общее:

- отдельный контейнер только для линий (не смешан с точками);
- порции + `requestAnimationFrame`;
- смена viewport → abort fetch + смена `generation` → старые чанки не дорисовываются;
- **кликов по линиям нет** (карточка только у точек с порога zoom).

**Yandex 2.1:** второй `ObjectManager`, `clusterize: false`, JSON `LineString`, координаты в `[lat, lon]`. Рисует overlay Яндекса.

**Yandex 3:** `YMapCollection` + `YMapFeature` с `LineString` (координаты как в GeoJSON). Стиль: `stroke: [{ width, color }]`, opacity через rgba. Сначала рисуются точки, линии — следом (быстрее ощущается первый кадр).

Упрощения на клиенте нет: что пришло с API, то и кладётся в менеджер/feature.

---

### 7. Чего линии намеренно не делают

- нет кластеризации;
- нет скрытия ниже zoom (линии «всегда», но прореженные);
- нет приоритета по типу/слою при отборе — только random;
- нет разрезания одной длинной линии «пополам» ради бюджета — только целиком;
- GIS не умеет simplify/zoom — всё режем у себя после полного (или truncated) ответа.

---

### Схема одной фразы

**Жест → bbox+zoom → GIS отдаёт сырые линии → отфильтровали → случайно урезали число линий → stride/DP по zoom → уложились в 5000 вершин → клиент порциями нарисовал в отдельном слое.**

Крутилки опыта: `GIS_MAX_LINE_VERTICES`, `GIS_LINE_SIMPLIFY_METERS`. Перезапуск API после смены `.env` достаточен.
